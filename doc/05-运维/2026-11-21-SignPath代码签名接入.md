## 一、前置事实

- 当前构建未签名：electron-builder 日志为 `no signing info identified, signing is skipped`。
- 自签名证书不能解决公开分发的 SmartScreen 提示，仅适合内网测试。
- 自动更新的签名校验与发布者名称相关；启用签名后需保证 `publisherName` 与证书主体一致。

## 二、申请需要准备的信息

1. 项目名称、仓库 URL、开源许可证（MIT）、项目简介与发布频率。
2. 维护者信息与发布流程：`main` + `release/vX.Y.Z` + `vX.Y.Z` tag + GitHub Release。
3. 需要签名的产物：
   - `光影工作志.exe`（win-unpacked 应用可执行文件）
   - `光影工作志 Setup X.Y.Z.exe`（NSIS 安装包）
   - `__uninstaller-nsis-lightframe-worklog.exe`（卸载器）
4. 签名策略建议：
   - 仅允许 `main` 分支与 `v*` tag 的构建；
   - 仅允许 release 工作流；
   - 拒绝 PR 构建与本地构建。

## 三、SignPath 侧操作（需项目所有者完成）

1. 在 SignPath 注册并提交 Foundation 开源项目申请，等待审核。
2. 审核通过后创建 Organization / Project，连接 GitHub 仓库（SignPath GitHub App）。
3. 创建 signing policy（建议命名 `release-signing`）与 artifact configuration。
4. 生成 API Token，保存为 GitHub Actions Secrets：
   - `SIGNPATH_API_TOKEN`
   - `SIGNPATH_ORGANIZATION_ID`
   - `SIGNPATH_PROJECT_SLUG`
   - `SIGNPATH_SIGNING_POLICY_SLUG`
   - `SIGNPATH_ARTIFACT_CONFIGURATION_SLUG`
5. 记录 SignPath 提供的 GitHub Action / CLI 版本与参数（以其当前文档为准）。

> 不要提交 Token、证书或任何私钥到仓库。

## 四、与 electron-builder 的两种接法

### 方案 A（推荐）：构建期自定义 sign hook

在 `package.json` 的 `build.win.signtoolOptions.sign` 指向一个签名脚本；electron-builder 会在生成
blockmap / latest.yml **之前**逐个调用它。脚本调用 SignPath 的签名 API 或 CLI，替换为已签名文件。
这样 `latest.yml` 的 size/sha512 与 blockmap 会基于签名后的字节生成，避免哈希失配。

需要实现的内容：
- `scripts/signpath-sign.js`：接收 electron-builder 传入的文件路径，提交 SignPath、轮询结果、替换文件；
- CI Secrets 注入；
- 失败时非零退出，阻止构建继续。

### 方案 B：构建后签名

先 `npm run dist`，再提交安装包/应用 exe 到 SignPath，下载签名产物。**必须**在签名后重新生成
`latest.yml` 与 `.blockmap`，否则自动更新会因 sha512 不匹配失败。此方案步骤更多，不优先。

## 五、CI 接入点（草案）

1. GitHub Actions 在 `v*` tag 触发；
2. `npm ci` → `npm run dist`（带 sign hook）；
3. 校验签名：
   ```powershell
   signtool verify /pa /v "dist\光影工作志 Setup X.Y.Z.exe"
   Get-AuthenticodeSignature "dist\光影工作志 Setup X.Y.Z.exe" | Format-List
   ```
4. 匿名验证 Release 资产与 `latest.yml`；
5. 发布 GitHub Release。

> SignPath 的 GitHub Action/CLI 参数以其审核通过时提供的文档为准；接入时先做一次
> `workflow_dispatch` 空跑，确认签名策略与 artifact configuration 匹配。

## 六、验收判据

- `Get-AuthenticodeSignature` 状态为 `Valid`，签名主体与 `publisherName` 一致；
- 安装包属性显示发布者，不再是 “Unknown publisher”；
- 自动更新能校验签名并成功安装；
- 未签名本地构建不会被误发布；
- Release 的 `latest.yml` size/sha512 与签名后资产一致。

## 七、回退与备选

- SignPath 审核未通过：改用 Azure Trusted Signing（需 Azure/Entra 组织资质）或购买 OV/EV 证书。
- 任何签名方案都需要证书/服务凭据；没有凭据时无法生成受信任签名。
- 签名不改变 SmartScreen 的“新发布者”信誉积累节奏；EV 通常更快，OV/Azure 可能需要时间。
