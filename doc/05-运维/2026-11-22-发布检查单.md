## 四、完整发布脚本

准备一个干净 worktree（示例路径 `../lightframe-worklog-clean`），其 HEAD 必须与待发布提交一致，
且 `git status --porcelain` 为空。安装包只在 worktree 内构建，不在日常开发目录打包。

```bash
node scripts/release.js \
  --version X.Y.Z \
  --change-card doc/02-需求分析/changes/<主题>.md \
  --review-evidence doc/03-设计/reviews/<主题>.md \
  --worktree ../lightframe-worklog-clean \
  --electron-dist ../lightframe-worklog-clean/node_modules/electron/dist \
  --old-app-dir "../lightframe-worklog-clean/dist-release-<上一版本>/win-unpacked" \
  --change-summary "<一句话变更摘要>"
```

可选参数：

- `--previous-version X.Y.<Z-1>`：`git describe` 无法推导上一版本时显式指定。
- `--absent-marker '"version": "X.Y.<Z-1>"'`：需要显式指定旧版本标记时使用。
- `--test-root <临时目录>`：更新下载验证的临时目录；默认在系统临时目录新建，不得指向日常安装或用户数据。
- `--skip-update`：仅在明确不做更新下载验证时使用；未传该参数时必须提供 `--old-app-dir`，缺失直接失败。

脚本会依次执行：

1. 预检（工作区、版本三件套、README；完整模式校验变更卡与评审证据）。
2. worktree 切到当前 HEAD，确认干净，逐文件 `node --check`，执行 `npm ci`、`npm test`、`npm run test:release`。
3. `smoke:boot`、`verify-lan --self-host`。
4. `electron-builder --win nsis --publish never` 构建安装包。
5. 运行时载荷正断言：`ffmpeg.dll`、`dxcompiler.dll` 存在且非空（不小于 1,000,000 字节），
   `resources/default_app.asar` 不存在。
6. 打包版 UI 烟测 3 次（端口 `9761/9762/9763`）。
7. `release_gate` 校验 asar 与安装包。
8. 将安装包、blockmap、`latest.yml`、发布说明复制到 `dist/`；`latest.yml` 的 `path` 与
   `files[].url` 改写为 `dist/` 中的新文件名，并用 version/size/sha512 与安装包实际值对账。
9. 更新下载验证（未显式 `--skip-update` 时）：调用 `tools/verify-update.js`，参数为
   `--old-app-dir <解包目录> --new-dir dist --test-root <临时目录> --log-file .release-logs/release-X.Y.Z.verify-update.log`。
10. 打印发布命令。

全过程写入 `dist/release-X.Y.Z.log`（步骤、命令与状态）；任一步失败也会保留该日志。

判据：脚本退出码为 0；上述每一步均 PASS；`dist/` 下资产齐全；`dist/release-X.Y.Z.log`
记录 `RESULT PASS`；更新验证日志保留；脚本只打印 `git push`、`git tag`、`gh release create`
命令，不自行执行。

## 六、更新下载验证（不运行安装器）

用旧版解包目录的副本 + 本地 generic feed，验证 electron-updater 的
检查 → 下载 → 哈希链路。脚本不运行任何 NSIS 安装/卸载，不触碰日常安装与用户数据。

完整发布脚本在未显式 `--skip-update` 时会自动执行本步，`--new-dir` 固定为仓库根下的 `dist/`
（发布材料已复制完成）。手工复跑时必须在仓库根执行：

```bash
node tools/verify-update.js \
  --old-app-dir "../lightframe-worklog-clean/dist-release-<旧版本>/win-unpacked" \
  --new-dir "dist" \
  --test-root "$TEMP/lw-update-e2e-<时间戳>" \
  --log-file ".release-logs/release-X.Y.Z.verify-update.log"
```

判据：

- `dist/latest.yml` 的 `path` 与 `files[].url` 指向 `dist/` 内实际安装包文件名。
- 输出 `UPDATE_DOWNLOADED`，其 `sha512` / `size` 与 `latest.yml` 声明一致；`sha256` 与本地/feed 安装包一致（`latest.yml` 不含 sha256）。
- 输出 `RESULT PASS` 与 `LOG_FILE=<绝对路径>`；日志在 PASS 后保留。
- `test-root` 已删除；隔离的 `LOCALAPPDATA` 缓存未残留。
- 无安装器进程；日常安装目录、日常用户数据与日常更新缓存的修改时间/哈希不变。
- 该步骤只证明下载链路；真实安装升级必须按下一节人工执行。

## 九、发布后匿名核验

仓库为公开仓库，自动更新依赖匿名访问；核验时不得携带 token，也不使用已登录的 `gh`。

```bash
curl -fsS https://api.github.com/repos/turnarond/lightframe-worklog/releases/latest
```

判据：

- 匿名 API 返回 `tag_name=vX.Y.Z`，`draft=false`、`prerelease=false`。
- 资产恰为 3 个：安装包、`.blockmap`、`latest.yml`。
- 匿名下载 `latest.yml`，其 `version`、安装包 `size`、`sha512` 与本地一致。
- 匿名下载安装包（或网络受限时用 asset Range `0-1023` 返回 206 并比对首段），
  sha256 与本地 `dist/` 安装包一致；GitHub asset digest 与本地 sha256 一致。
- 若整包匿名下载失败，必须记录失败现象，并以 Range 206 + digest 对账 + `latest.yml`
  匿名 200 作为替代证据，写明证据局限。

## 十、tag 与 Release（需单独授权）

前置：最终提交 CI 全绿；`release/vX.Y.Z` 已按约定合入 `main`；版本三件套与检查单均已复核。
tag 必须打在该合入提交上，使用附注 tag。

发布脚本打印的命令（示例，执行前逐条获得授权）：

```bash
git push origin main
git tag -a vX.Y.Z -m "vX.Y.Z · YYYY-MM-DD"
git push origin vX.Y.Z
gh release create vX.Y.Z \
  dist/lightframe-worklog-setup-X.Y.Z.exe \
  dist/lightframe-worklog-setup-X.Y.Z.exe.blockmap \
  dist/latest.yml \
  --notes-file dist/release-notes-X.Y.Z.md
```

判据：

- tag 指向 `main` 的发布提交：`git rev-parse vX.Y.Z^{commit}` 与 `git rev-parse main` 一致。
- Release 为 Latest，非草稿、非预发布；资产恰为 3 个。
- tag 触发的 CI 全绿；安装包未签名时在 Release 说明与 README 中保留 SmartScreen 提示。
- 发布后按第九节重新做一次匿名核验。

## 十一、回滚

- 发布前失败：删除本地 tag / 丢弃构建产物，不推送、不创建 Release，修复后重新走完整流程。
- 已推送但发现阻断问题：
  - 将 Release 标记为 Pre-release，或删除 Release 并保留 tag，使 `releases/latest` 回到上一版本；
  - 自动更新随 `latest` 回退；不覆盖已发布 tag，修复走新的补丁版本。
- 数据兼容：升级新增的数据目录/字段必须向前兼容；回装旧版前确认旧版不会读取并破坏新数据。
- 回滚后补写发布记录，写明原因、影响版本、回退目标与用户处置建议。

- 未获授权直接 push、打 tag、创建/修改 GitHub Release。
