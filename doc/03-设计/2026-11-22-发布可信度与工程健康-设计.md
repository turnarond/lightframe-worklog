# 发布可信度与工程健康设计

- 版本：v2.12.0（Phase 1）/ v2.13.0（Phase 2，建议）
- 日期：2026-11-22
- 状态：待评审
- 上游：v2.11.1 发布事故复盘、`agents.md` 工程门禁、产品规格边界
- 下游：实施计划（设计评审通过后编写）

## 1. 背景

v2.11.0 首次采用运行时 DLL 裁剪，在无 GPU / 软件渲染环境出现渲染进程无响应；CI 与 tag 运行均在
Packaged UI smoke 悬挂。虽然 v2.11.1 已通过恢复 `ffmpeg.dll` / `dxcompiler.dll` 修复并发布，但暴露出三个问题：

1. 发布仍依赖人工记忆与临时诊断，缺少可重复的“构建 → 门禁 → 自动更新验证 → 发布材料”流程。
2. 打包版 UI 烟测此前没有超时/进度日志，悬挂时无法定位。
3. `src/renderer.js` 2061 行、`src/styles.css` 1648 行、`main.js` 930 行，超过工程手册 600 行阈值；
   发布修复与后续同步改造都在这三个大文件里进行，回归成本高。

本设计分两阶段：Phase 1 先把发布链路做可信，Phase 2 再做拆分与定向清理。两阶段都不改变产品边界。

## 2. 目标与非目标

### Phase 1 目标

- 用一个发布脚本完成干净构建、门禁、产物哈希、发布说明与资产清单；**不自动 push/tag/Release**。
- 用本地更新服务器验证 electron-updater 的检查、下载与哈希；完整安装路径在隔离测试环境中可选执行。
- CI 增加发布预检（不构建），保留 v2.11.1 的运行时 DLL 与 UI 烟测断言。
- 统一“运行时完整性”文档口径，补发布/回滚检查单。

### Phase 2 目标

- 把 `main.js` 拆成窗口/托盘/提醒/IPC/状态模块，入口降到约 100 行。
- 把 `renderer.js` 按状态、DOM、UI、挂件、任务、日报周报、设置同步备份拆成模块；保留单一入口。
- 把 `styles.css` 按 base / components / tasks / reports / widget / settings / motion 拆分，清理死代码。
- 每个切片保持行为不变，由 168 测试与打包版 UI 烟测锁回归。

### 非目标

- 不新增用户可见功能，不改任务/日报/同步协议与 LWW 规则。
- 不引入状态框架、TypeScript 或构建工具（Phase 2 仍是无构建的模块拆分）。
- 不做代码签名；SignPath 仍暂缓。
- 不把完整安装器升级测试放进 GitHub CI（Windows 安装器/UAC 不适合托管 runner）。
- 不做服务端部署、监控或冲突合并 UI；这些属于后续同步可信度项目。

## 3. 已确认决策

| 决策 | 结论 |
|---|---|
| 下一阶段路线 | 工程健康 + 发布可信度（A） |
| 重构深度 | 拆分 + 定向清理（B），不引入状态框架/构建工具 |
| 内部顺序 | 先发布可信度，再拆分 |
| 自动更新验证 | 本地端到端；默认验证检查/下载/哈希，完整安装仅在隔离测试环境执行 |
| 发布脚本边界 | 构建+验证+生成说明；push/tag/Release 仍需单独授权 |
| 版本建议 | Phase 1 → v2.12.0；Phase 2 → v2.13.0 |

## 4. Phase 1 架构

### 4.1 模块边界

| 组件 | 职责 |
|---|---|
| `scripts/release.js`（新增） | 发布预检、干净构建、门禁、哈希、Release 说明与资产清单；不执行 push/tag/Release |
| `tools/verify-update.js`（新增） | 本地更新服务器、临时安装旧版、替换 `app-update.yml`、electron-updater 检查/下载/哈希；可选隔离安装验证 |
| `.github/workflows/ci.yml` | 保留运行时 DLL 正断言；增加 `release.js --check` 预检步骤 |
| `doc/05-运维` | 发布检查单、回滚与自动更新验证说明 |

### 4.2 `scripts/release.js`

CLI：

```text
node scripts/release.js --version 2.12.0 \
  --change-card doc/02-需求分析/changes/<卡>.md \
  --review-evidence doc/03-设计/reviews/<证据>.md \
  [--worktree ../lightframe-worklog-clean] \
  [--electron-dist <Electron 目录>] \
  [--old-installer <上一版安装包>] \
  [--test-root <临时目录>] \
  [--skip-update] [--update-install] [--check]
```

步骤：

1. **预检**：工作区干净；版本三件套一致；tag 不存在；变更卡/评审证据路径存在且检查器通过。
2. **干净构建**：优先使用 `--worktree` 指定 worktree；`npm ci` 后检查 Electron 二进制；
   缺失时使用本地缓存 `%LOCALAPPDATA%\electron\Cache` 或 `--electron-dist`，不静默联网。
3. **门禁**：168 测试、逐文件语法、`smoke:boot`、`verify-lan`、`pack:dir`、打包版 UI 烟测 3 次、
   `release_gate`（asar 标记/缺席、安装包 md5、变更卡/评审证据）。
4. **产物**：计算 SHA-256/SHA-512/MD5；把安装包、blockmap、`latest.yml` 暂存到 `dist/`；
   生成 `release-notes-<version>.md` 与资产清单。
5. **更新验证**：若提供 `--old-installer` 且未 `--skip-update`，调用 `tools/verify-update.js` 的下载校验；
   完整安装需要显式 `--update-install` 与隔离测试环境。
6. **输出**：打印需要人工授权的命令：

```text
git push origin main
git tag -a vX.Y.Z -m "..."
git push origin vX.Y.Z
gh release create vX.Y.Z ... --notes-file release-notes-X.Y.Z.md
```

失败语义：任一步失败立即非零退出，不生成“可发布”结论；日志写入 `dist/release-<version>.log`。
`--check` 只做预检与文档检查，不构建、不联网，供 CI 使用。

### 4.3 `tools/verify-update.js`

目标：在不触碰日常安装与真实数据的前提下，验证 electron-updater 的完整下载链路。

- **旧版安装**：用 NSIS `/S /D=<test-root>\app` 安装上一版到临时目录，userData 指向 `<test-root>\data`。
- **注入 feed**：替换临时安装 `resources/app-update.yml` 为 `provider: generic`、本地服务器 URL；
  不改产品代码，也不需要旧版包含任何测试钩子。
- **本地更新服务器**：在 `127.0.0.1` 随机端口提供 `latest.yml`、blockmap 与新版安装包；
  `latest.yml` 的 URL 由测试服务器动态重写。
- **触发检查**：用 CDP 调用 `window.api.checkUpdate()`，等待 `app:update-status` 中的
  `update-downloaded`；校验下载文件大小与 SHA-256 等于新版安装包。
- **完整安装（可选）**：`--update-install` 在**隔离的 Windows Sandbox/测试用户**中执行
  `quitAndInstall`，随后核对新 asar 版本。工具要求 `--test-root` 位于临时目录，并拒绝在
  `C:\Program Files\lightframe-worklog` 或 `%APPDATA%\lightframe-worklog` 对应的日常安装/数据环境执行。
- **清理**：结束后终止进程、删除临时安装与 userData；失败时保留日志路径。

### 4.4 产品代码影响

Phase 1 不修改 `main.js` / `preload.js` / 渲染层；更新验证通过临时安装配置完成。发布构建与日常运行
不会读取任何测试环境变量。

默认模式只验证检查/下载/哈希，不运行安装器；完整安装作为发布检查单中的可选步骤，避免误升级日常安装。

### 4.5 CI 与文档

- CI 增加 `node scripts/release.js --check`（仅预检/文档检查，不构建），放在现有 Windows gates 中。
- 保留运行时 DLL 正断言、UI 烟测超时/看门狗、`Verify packaged Electron version`。
- 新增发布检查单：版本三件套、变更卡/评审证据、3 次烟测、更新下载验证、资产哈希、匿名核验、tag/Release 授权。
- 统一文档口径：不再称“瘦身”，改为“运行时完整性”；注明 v2.11.0 预发布原因与 v2.11.1 替代关系。

## 5. 发布与更新流程

```text
release.js --check        # 预检
release.js --version ...  # 干净构建 + 门禁 + 产物 + 更新下载验证 + 发布材料
（人工授权）
git push main → tag → push tag → gh release create
（发布后）
release.js 生成的资产清单 + 匿名核验 + 回滚检查单
```

## 6. 错误与边界

- 工作区不干净、tag 已存在、版本三件套不一致：直接失败。
- Electron 缓存缺失且禁止联网：失败并提示可用 `--electron-dist`，不静默降级。
- 旧安装包缺失：默认跳过更新验证并显式警告；发布前必须补齐。
- 更新服务器端口占用：换随机端口；`latest.yml` 中的 URL 由测试服务器动态替换。
- 完整安装检测到日常安装/日常 userData：拒绝执行，要求隔离环境。
- 更新下载失败、哈希不一致：失败并保留日志与临时目录。
- UI 烟测悬挂：15 秒 CDP 超时 + 180 秒看门狗，输出应用日志后失败。

## 7. 验收判据

- `release.js --check` 在 v2.11.1 / v2.12.0 上通过，不产生 push/tag。
- 发布脚本本地完整运行（不带 `--check`，不执行远端操作）通过：168 测试、语法、`smoke:boot`、
  `verify-lan`、3 次 UI 烟测、`release_gate`。
- `verify-update.js` 用上一版安装包启动旧版，完成 check → download → 哈希校验；
  `--update-install` 在隔离环境验证新 asar 版本。
- CI 保留运行时 DLL/烟测断言，新增 `--check` 步骤后全绿。
- 不改变产品行为；发布脚本不自动执行 push/tag/Release。

## 8. Phase 2 拆分轮廓

按“可独立合并、行为不变”的切片执行：

1. `main.js` → `main/state`、`main/window`、`main/tray`、`main/reminders`、`main/ipc`；入口保留启动顺序。
2. `renderer.js` → `renderer/state`、`dom`、`ui`、`widget`、`tasks`、`reports`、`settings-sync-backup`；
   优先 ES modules + 单一入口，保留现有 DOM/事件顺序。
3. `styles.css` → `styles/base`、`components`、`tasks`、`reports`、`widget`、`settings`、`motion`；
   在 `index.html` 按原顺序加载，避免层叠变化。
4. 每个切片一提交；纯函数抽成可单测模块；每片至少一次打包版 UI 烟测。
5. 不做状态框架、类型系统或打包器；超过 600 行的新文件视为切片失败。

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 更新测试误升级日常安装 | 默认只下载校验；安装模式要求隔离环境、`--test-root` 位于临时目录并显式 `--update-install` |
| 替换 `app-update.yml` 后旧版仍访问 GitHub | 启动前校验临时安装的 `resources/app-update.yml` 已指向本地 URL；失败即停 |
| electron-updater 对未签名包的提示/行为差异 | 在本地 Windows 实测并记录；不把安装测试放进 CI |
| 发布脚本误操作远端 | 脚本只打印命令；push/tag/Release 由人工授权 |
| 拆分改变 DOM/事件顺序 | 每切片跑 UI 烟测；纯函数先抽、DOM 层后拆；不做大爆炸重构 |
| ES modules 在 file:// / CSP 下加载失败 | 第一个切片先做最小 spike；失败则回退到按顺序加载的经典脚本 + 显式命名空间 |
| CSS 拆分改变层叠 | 按原顺序加载，先机械移动再清理；每次对比首屏截图 |
| 文档/版本 token 漂移 | `release.js --check` 校验版本三件套、README 当前版本与变更卡/证据 |

## 10. 开放问题

无。路线、重构深度、内部顺序、更新验证层级、发布脚本边界均已确认。
